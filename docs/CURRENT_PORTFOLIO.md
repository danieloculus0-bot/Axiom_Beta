## Architecture ownership

**Scope boundary:** Axiom is the manufacturing/ERP product only. BEAN may provide optional intelligence through defined interfaces. AIscend, FUN/games, BEAN-Rider, venvWin and unrelated experiments are not Axiom components. Portfolio links are navigation, not functional integration evidence.

- **ForgeVault** owns released drawing bytes and version/revision identity. **EZ-FAIR** owns dimension proposals. **Axiom** stores an imported, review-required FAI. The Windows/Linux CI validates this local data path and source SHA; it is **not yet a shared-server authenticated data connector**.
- **BEAN Core** maintains persistent evidence research; **BEAN AI Bridge** provides evidence adapters; **EZ-FEA** owns the physics engine. The tested handoffs do not imply Core is performing autonomous numerical analysis or self-repair.
- **MFGForge** is the older ERP source foundation; **SuperForge Unofficial** is release-artifact planning. The current consolidation target is **Axiom**. Copied source snapshots are not live inter-app synchronization.
- **AIscend, FUN, 64Δ, and venvWin** remain separate projects and keep distinct validation and licensing requirements.

## Documentation practice

1. Keep READMEs small: supported implementation, setup, limits, direct CI receipts and short next priorities.
2. Put dated research/milestones and superseded architecture in archived documents. Never delete history during landing-page cleanup.
3. Do not treat a prior Windows installer job or unit-test success as evidence of live production deployment.
4. Reuse [Gothic Lime design tokens](BEAN_GOTHIC_LIME_DESIGN.md) while keeping applications independently functional.
5. Recheck the linked GitHub Actions before a build/release; this index is a **dated snapshot, not a dynamic dashboard**.
